# Architecture

Dogfood Portal is a single deployable unit: one Node.js process serves the
JSON API, the static web app and uploaded images, backed by one PostgreSQL
database. It runs fully offline. There are no CDNs, no external email or
auth providers and no telemetry.

```
┌───────────────────────── docker compose ─────────────────────────┐
│                                                                  │
│  app (node:24-alpine, non-root)              db (postgres:16)    │
│  ┌────────────────────────────────────┐      ┌────────────────┐  │
│  │ Express 5                          │      │ schema + RLS   │  │
│  │  ├─ /api/*      JSON API (116 ops) │ SQL  │ triggers       │  │
│  │  ├─ /uploads/*  images (nosniff)   ├─────►│ audit chain    │  │
│  │  ├─ /.well-known signing key       │ role │                │  │
│  │  └─ /*          SPA (React)        │ dogfood_app          │  │
│  │ webhook worker (2 s tick)          │      └────────────────┘  │
│  └───────▲────────────────────────────┘      internal network    │
│          │ :8000                             (no route out)      │
└──────────┼───────────────────────────────────────────────────────┘
           │
   browser · API clients · acceptance runner · webhook receivers
```

## Repository layout

```
src/
  core/   @dogfood/core: pure TypeScript shared by API and web. No I/O.
          roles.ts (capability matrix) · schemas.ts (Zod inputs) · types.ts (DTOs)
          normalization.ts · bradley-terry.ts · assignment.ts · timeline.ts
          voting.ts · csv.ts
  api/    @dogfood/api: Express app, bundled by esbuild into dist/server.mjs + dist/cli.mjs
          migrations/*.sql · src/http (route table, middleware, rate limit)
          src/modules/* (one file per domain) · src/db · src/seed · src/lib
  web/    @dogfood/web: Vite + React 19 + Tailwind v4 SPA
          src/ui (Material 3 Expressive kit) · src/pages · src/components · src/lib
tests/
  unit/          algorithms (Vitest)
  integration/   real Postgres + real HTTP app, one throw-away DB per file
acceptance/run.py  stdlib-only tier-by-tier checker (writes acceptance-report.txt)
tooling/           shared ESLint and TypeScript configs
fixtures.json      deterministic seed data (generated by scripts/generate-fixtures.py)
```

`@dogfood/core` is the heart of the system. Scoring, normalization,
routing, deadline and voting-window rules, the capability matrix and every
input schema are pure functions there. The same code validates a form in
the browser and the request on the server, and it is tested without a
database.

## Request lifecycle (API)

1. **Security middleware.**
   - Sets the CSP, `X-Frame-Options`, `nosniff`, `Referrer-Policy` and
     `Permissions-Policy` headers, and removes `X-Powered-By`.
   - Applies a global token bucket per IP.
   - Enforces JSON body limits and turns malformed JSON into a 400
     `BAD_JSON`.
2. **Actor resolution.**
   - Reads the Bearer token or the `dogfood_session` cookie, hashes it with
     SHA-256 and looks it up together with the user's current role and
     `disabled_at`.
   - Computes the keyed IP hash and the UA hash.
   - The result is `req.actor`.
3. **CSRF guard.** Cookie-authenticated writes whose `Origin` doesn't match
   are refused.
4. **Route table.** Every endpoint is declared once with `route({...})` in
   `src/api/src/modules/*.ts`:

   ```ts
   route({
     method: "put", path: "/api/judge/assignments/:assignmentId/ballot",
     summary: "Save or submit your rubric scores for an assignment",
     auth: "judging:score",            // capability from @dogfood/core roles.ts
     body: scoreInput,                 // Zod schema → validation + OpenAPI
     rateLimit: { bucket: "write", spec: LIMITS.write },
     async handler({ app, params, body, actor, tx }) { … },
   })
   ```

   `mountRoutes` enforces auth, the role capability, rate limits and
   body/query validation, which return `VALIDATION_FAILED` with per-field
   details. It then calls the handler. `openApiDocument` generates
   `/api/openapi.json` (OpenAPI 3.1) **from the same table**, using
   `z.toJSONSchema`. A route cannot exist undocumented;
   `platform.test.ts` asserts this.
5. **Transactions under RLS.**
   - `tx(fn)` opens a transaction, runs `SET LOCAL ROLE dogfood_app` and
     sets `app.user_id` and `app.role`. Row-Level Security therefore filters
     every query the handler runs.
   - Trusted internal jobs use `db.system()`: seeding, the normalization
     snapshot, record issuing and the webhook worker.
   - Only migrations and boot-time secret handling use the owner
     connection.
6. **Errors.**
   - Every failure leaves the API as
     `{ error, code, details? }` with the right HTTP status.
   - Postgres errors raised by our triggers are mapped to the same codes.
     For example, the deadline trigger becomes `DEADLINE_PASSED`.
   - Unknown errors are logged server-side and returned as a generic
     `INTERNAL`, never with a stack trace.

## Time

A single injectable clock, `app.now()`, drives every rule that depends on
time: deadlines, voting windows, judging close, invite and code expiry, and
rate-limit refill. Rules live in `@dogfood/core/timeline.ts` as pure
functions of `(event, now)`. Client time headers are ignored. The web app
estimates server skew from the `Date` header and renders countdowns in
server time. Integration tests inject a controllable clock to drive a whole
event lifecycle in seconds. The acceptance runner does the same on the live
stack by waiting for a real 14-second deadline.

## Domain modules (`src/api/src/modules`)

| Module | Responsibility |
|---|---|
| `auth` | Register, login, logout, `me`, API tokens (scrypt, hashed sessions) |
| `access` | Loading events with tenancy rules (`loadVisibleEvent`, `loadManagedEvent`), judge scope, team lookup |
| `events` | Event CRUD, lifecycle (publish/archive), tracks, prizes, questions, criteria, registration, co-organizers |
| `teams` | Teams, invites (single-use, race-safe), membership, roster lock |
| `submissions` | Drafts, completeness checks, submit/unsubmit, gallery (search, facets, per-viewer shuffle), eligibility, extensions, uploads |
| `judging` | Judge invites, panel, conflicts, algorithmic and manual assignment, ballots, recusal, pairwise |
| `results` | Normalization runs, publish/unpublish, public leaderboard, Bradley–Terry ranking, CSV exports |
| `voting` | Open, email and authenticated voting; single and quadratic styles; Sybil flags; tallies; comments |
| `webhooks` | Outbox-pattern emission inside the domain transaction; a leased, concurrent, retrying delivery worker; HMAC signing |
| `records` | Ed25519-signed participation, judging and winner records; public verification; the key at `/.well-known` |
| `platform` | Event bundle export/import, bulk registration CSV, embed feed (CORS) |
| `admin` | Users and roles, audit views and chain verification, local outbox, stats |

**Webhooks.** Emission uses the outbox pattern:
`webhooks.emit(eventId, type, data, tx)` inserts delivery rows **in the same
transaction** as the domain change, so a rolled-back change emits nothing.
The worker then works through due rows:

- It claims up to 20 rows by leasing them: `next_attempt_at` is pushed 60 s
  ahead in the same statement.
- It POSTs them concurrently with a 5 s timeout.
- It retries with exponential backoff (5·2ⁿ s) for up to 6 attempts.

## Web app (`src/web`)

- **Routing and data.** React Router 7 with lazy route chunks. Server state
  goes through TanStack Query; there is no global client store.
- **API client.** `lib/api.ts` maps `{ code, details }` errors onto form
  fields.
- **Session and clock.** `lib/session.tsx` holds the session;
  `lib/time.ts` provides a server-synced clock.
- **Design system: Material 3 Expressive, implemented in Tailwind v4.**
  - **Color.** `scripts/generate-theme.mjs` uses
    `@material/material-color-utilities` (2025 spec, `SchemeVibrant`, seed
    `#6750FF`) to generate light and dark tonal palettes as CSS variables
    in `styles/theme.css`. Extra *success* and *warning* roles are
    harmonised to the seed.
  - **Tokens.** `styles/app.css` maps the palettes onto Tailwind `@theme`
    tokens: color roles, the type scale (`type-display-lg` …
    `type-label-sm`), a shape scale up to `rounded-full`, elevation, and
    motion easings such as spring-fast.
  - **Type and icons.** Fonts are Google Sans Flex (with the `ROND` axis)
    and JetBrains Mono, both self-hosted via fontsource. Material Symbols
    are compiled into an SVG subset (`icons.generated.ts`) of only the
    icons we use.
  - **Shapes.** The M3 Expressive shape library (cookie, clover, burst,
    gem, …) is generated procedurally as SVG paths, with no image assets.
  - **Components** (`src/ui`): buttons with shape morphing, FAB, button
    groups, chips, text fields, sliders, switches, tabs, dialogs, menus,
    toasts, wavy and linear progress, and the loading indicator. They use
    state layers and focus rings, and respect `prefers-reduced-motion`.
- **Screens.**
  - Public: home, events, event, gallery, project, results, embed, verify
    and API docs.
  - Participant: dashboard, team and invites, submission editor with a
    deadline countdown.
  - Judge: queue, scoring with rubric sliders, pairwise.
  - Organizer: overview, settings, setup, rubric, submissions, judges and
    routing, Results Lab (raw vs normalized strip plots, judge bias,
    invariants), votes, audit, integrations.
  - Admin.
- **Charts** are small, dependency-free SVG components that follow data-viz
  rules: thin marks, hairline grids, text in text tokens, keyboard- and
  hover-accessible tooltips.

## Security architecture (summary)

Defence in depth: each rule is enforced at the outermost layer that can
give a good error, **and** at the innermost layer that can't be bypassed.

| Concern | Outer layer | Inner layer |
|---|---|---|
| Who may call an endpoint | Capability matrix in the route table | — |
| Which rows a judge sees | Explicit `judge_id = $me` predicates | Postgres RLS (`FORCE`) on assignments, ballots, scores, pairwise votes and normalization runs |
| Deadline | `assertBeforeDeadline(app.now())` | `submissions_deadline` trigger |
| Score bounds, ballot ownership | Rubric validation | `scores_10_bounds` and `*_00_ownership` triggers |
| History integrity | Audit writes in the same transaction as each change | Append-only grants and trigger, SHA-256 chain, `audit_log_verify()` |
| Secrets | Server-only code paths | `settings` not readable by the request role |

See THREAT-MODEL.md for threats, residual risks and the deployment checklist.

## Testing strategy

| Layer | Tooling | What it proves |
|---|---|---|
| Unit (`tests/unit`, 57 tests) | Vitest | Normalization maths and invariants; the Bradley–Terry MLE balance condition and convergence; routing balance, conflicts and scope; timeline rules; CSV injection; hash distribution |
| Integration (`tests/integration`, 93 tests) | Vitest + real Postgres + real HTTP | Auth and RBAC; RLS isolation with raw SQL as the app role; deadline and DB trigger; single-use invites under a race; a full event lifecycle on a controlled clock; voting abuse controls; webhooks against a real receiver; Ed25519 verification and tampering; OpenAPI coverage; audit tamper detection |
| Acceptance (`acceptance/run.py`, 38 checks) | Python stdlib, black-box HTTP | The claimed tiers T1–T4 plus bonuses, against the running stack (Docker, or native), with maths recomputed independently |

`pnpm test` runs unit and integration tests. It needs a local Postgres;
set `TEST_DATABASE_URL` to point at one. `pnpm test:acceptance` writes
`acceptance-report.txt`.

## Build and deployment

- **Build.** The multi-stage `Dockerfile` installs the pnpm workspace,
  bundles the API with esbuild into two ESM files (`@dogfood/core`, Express,
  `pg` and Zod included) and builds the SPA. The runtime stage copies only
  `dist/`, `migrations/`, the web `dist/` and `fixtures.json`: no
  `node_modules`, no compilers, a non-root user, and a healthcheck on
  `/api/health`.
- **Boot.** The same boot sequence runs for the server and the CLI, and it
  is idempotent:
  1. Wait for the database.
  2. Apply migrations under an advisory lock.
  3. Create the app secret and signing key if they are missing.
  4. Seed the fixtures if the database is empty.
  5. Refresh the checker sessions.
  6. Listen, and start the webhook worker.

  `SIGTERM` drains and closes the server gracefully.
- **Compose.** `app` plus `db`. The database sits on an `internal: true`
  network and is never published. `app` also joins an `edge` network for
  its published port, and for optional webhooks to receivers on the host
  (`host.docker.internal`). Detaching `app` from `edge` leaves the stack
  fully air-gapped; the acceptance suite still verifies T1–T4 that way.

## Key decisions

| Decision | Why |
|---|---|
| Modular monolith, one process | Self-hosting on a laptop or a single VM is the target. There are fewer moving parts to run offline, and transactions span every domain. |
| PostgreSQL rather than SQLite | Row-Level Security, triggers, `timestamptz`, advisory locks, generated `tsvector` search and JSONB. The isolation guarantees depend on them. |
| Shared pure core | One implementation of scoring, rules and schemas, tested in isolation and used identically by the API and the UI. |
| Route table → OpenAPI | Documentation cannot drift from behaviour. API-first is structural, not aspirational. |
| Bundled API (esbuild) | A tiny runtime image, fast cold start, no install step at deploy time. |
| In-memory rate limiter | Correct for a single node. A documented limitation for multi-node deployments. |
| Local mail outbox | Email-gated voting works offline. An SMTP relay can be added later without schema changes. |
