# 04 — Constraints

## 1. Hackathon Constraints

* **Eligibility:** Global, online, free to participate; open to developers, students, researchers, full-stack, backend, API, security, DevOps, and data engineers worldwide.
* **Team Size:** Solo developers or teams of 1 to 4 members.
* **Hackathon Duration:** 72 continuous hours (global online engineering sprint).
* **Submission Deadline:** September 28, 2026 at 18:00 UTC (strict code freeze timestamp).
* **Submission Format:** Public GitHub repository link + 5-minute recorded demo video.
* **Required Deliverables:**
  * Public GitHub repository containing source code.
  * `README.md` (environment requirements, Docker launch commands, default test credentials).
  * `ARCHITECTURE.md` (component diagrams, state flow, boundaries, trade-offs).
  * `DATA-MODEL.md` (entity-relationship schema, indexes, state machine transitions).
  * `JUDGING.md` (routing mechanics, score normalization math, security isolation model).
  * `docker-compose.yml` (root orchestration file).
  * `src/` (production source code).
  * `tests/` (unit, integration, and security role isolation tests).
  * `acceptance-report.txt` (plain text output generated by running automated test suite against local stack).
  * `LICENSE` (OSI-approved open source license file).
  * `.dogfood.toml` (capabilities manifest declaring functional tiers and entry points).
  * **5-Minute Demo Video:** Demonstrating single-command deployment, user role workflows, deadline enforcement, score normalization, and air-gapped offline operation.
* **Repository Requirements:** Public GitHub repository with a standardized file structure; no non-standard layout deviations that break test automation.
* **Demo Requirements:** 5-minute video proving local startup, role execution, deadline enforcement, scoring normalization, and offline functionality.
* **Presentation Requirements:** Video submission required; live presentation or Q&A sessions are unstated in official rules.

---

## 2. Technology Constraints

* **Required Technologies:** Docker and Docker Compose (`docker-compose.yml`) for containerized local orchestration.
* **Allowed Technologies:** Any programming language, framework, database, or tech stack that executes entirely within local Docker containers. AI coding tools (Claude Code, Cursor, Aider, GitHub Copilot, local models) are permitted.
* **Prohibited Technologies:** Third-party cloud SaaS services, managed cloud databases, hosted authentication providers (Auth0, Clerk, Firebase, etc.), external email APIs, or remote third-party SaaS APIs.
* **Required APIs / Platforms:** Self-contained backend API providing REST/GraphQL endpoints and webhooks (for Tier 4 extensions).
* **API / Service Restrictions:** 100% offline air-gapped execution required with network interfaces disabled. No external HTTP/HTTPS calls during judging or evaluation.
* **AI / LLM Restrictions:** AI assistants are permitted for scaffolding, boilerplate, and development velocity. Code is evaluated on correctness, architecture, maintainability, and security isolation.
* **Third-Party Dependency Restrictions:** Zero external cloud runtime dependencies. All language runtime libraries and dependencies must be encapsulated within local Docker images.
* **Open-Source / Licensing Requirements:** Must include an OSI-approved open-source license file (`LICENSE`) in the repository root (e.g., MIT, Apache 2.0).
* **Existing Code / Project Restrictions:** Submissions must be open-source. Code written prior to official kickoff (September 25, 2026 at 18:00 UTC) is restricted; pre-event planning, research, and prompt preparation are allowed.

## 3. Product Constraints

* **Target Users:** 5-tier role hierarchy enforced via session authentication: Visitor, Participant, Judge, Organizer, and Admin.
* **Supported Platforms:** Linux / Docker container environment launching via `docker compose up`.
* **Required Functionality:**
  * **Tier 1 (T1) Core Foundation:** Session auth, 5-level RBAC, event/track setup, team invite links, project drafts, server-side UTC hard deadline validation, searchable public gallery.
  * **Tier 2 (T2) Evaluation Engine:** Judge routing/assignments, weighted rubrics, backend query isolation (`WHERE judge_id = auth.uid`), Z-score statistical score normalization with Min-Max fallback, CSV exports.
  * **Automated Seed Data:** Deterministic startup seed scripts populating test users, events, rubrics, and submissions.
  * **Automated Acceptance Report:** Automated test runner executing against the stack and writing pass/fail logs to `acceptance-report.txt`.
* **Data Sources:** Local containerized database populated on boot via deterministic seed scripts.
* **User Workflows:** Registration → Team formation via invite link → Draft submission → Hard UTC deadline lock → Automated judge assignment → Rubric evaluation → Z-score normalization → Public gallery/voting → CSV score export.
* **Scope:** Functional correctness of Tier 1 and Tier 2 strictly takes precedence over incomplete Tier 3 or Tier 4 stretch features.
* **Features That Must or Must Not Be Included:**
  * *MUST include:* 5-level RBAC, server-side UTC deadline enforcement, backend query isolation (`WHERE judge_id = auth.uid`), Z-score statistical normalization, single-command Docker launch, `acceptance-report.txt`.
  * *MUST NOT include:* UI-only frontend authorization, raw score un-normalized averages as final rankings, or reliance on external cloud services.

---

## 4. Data & Privacy Constraints

* **User Data:** Account credentials managed via local session-based authentication stored in the local database.
* **Personal Information:** Managed locally within isolated containers; zero telemetry or transmission to external cloud services.
* **Sensitive Data:** Score sheets and evaluation ballots must be strictly isolated to assigned judges (`WHERE judge_id = auth.uid`). Unassigned judges or participants MUST NOT see other judges' raw evaluations.
* **Data Storage:** Local containerized database instances persistent across container restarts.
* **Data Sharing:** CSV export utilities for evaluation metrics and project scores.
* **Data Retention:** Retained in local container storage for historical audit trails.
* **Privacy & Security:** Row-level or backend controller-level query isolation; anti-Sybil IP duplicate detection and rate limiting for public community voting.
* **Third-Party Data:** Zero reliance on external third-party data services.

## 5. Resource Constraints

* **Budget:** Free participation ($0 fee).
* **API Usage:** Local offline API endpoints only; zero paid API services.
* **Compute:** Must execute within standard local Docker environment resources.
* **Cloud Services:** $0 allowed / Zero cloud services permitted.
